意图识别与多 Agent 协同编排（大脑与路由层）

架构选型依据 · 状态管理 · 死锁熔断 · 人机协同
Q1 架构权衡 SOP vs ReAct
架构权衡：你提到弃用了纯自主循环（如 ReAct），改用“SOP 确定性工作流 + 局部动态路由”，能结合具体业务场景说说，哪些环节是严格写死 SOP 的？哪些环节允许大模型做局部动态路由？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“在医保基金审计这种高合规、高确定性的场景下，纯 ReAct 循环是绝对不可控的，模型容易在多轮工具调用中迷失方向或产生死循环。因此我们系统将骨干链路设计为严格确定性的状态机 SOP：

从用户问题输入，必须严格依次经过 Aligner（白盒意图对齐） -> Planner（意图与逻辑规划） -> SQLEXEC（代码/SQL执行） -> Critic（反思核验） -> Consolidator（经验沉淀） -> Reporter（客观报告合成）。

而局部动态路由仅开放给受控的两个决策节点：

  1. FastRouter 前置分流：如果命中已知规则或算法模板，直接短路（Short-circuit）跳过 LLM 规划与生成，直达执行层；
  2. Critic（反思节点） 条件边：当执行报错或触发门控拦截时，由 Critic 依据错误类型动态决定是打回给 Planner（意图理解偏差，重做业务解耦）还是打回给 SQLEXEC（语法或字段错误，仅做 SQL 微调），或者升级到 Human-Approval（挂起人工审批）。”
【深度原理解释】

为什么不能用纯 ReAct？ ReAct 把“规划-行动-观察”交给 LLM 自由循环，在复杂任务中（比如查询跨省异地就医多表关联），LLM 经常在调用了 2 次工具后产生幻觉，以为自己拿到了完整数据就开始胡编；或者由于返回数据过长直接上下文爆炸。

为什么写死 SOP？ 审计业务讲究“留痕”与“证据链闭环”，每一个案件必须有清晰的意图记录、执行 SQL 记录、客观行数统计、反思校验记录，必须依赖确定性的状态转移保障工程下限。

Q2 意图识别 FastAuditRouter ArchetypeRegistry
意图识别设计：前置意图识别具体是怎么实现的？是用小模型分类、向量相似度匹配，还是直接用大模型做 Function Calling？如果用户输入非常模糊或包含多个复合意图，路由层怎么处理？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们的意图路由采用的是分层漏斗架构（Tiered Router）：

  1. 第一层（规则与轻量过滤）：通过 FastAuditRouter 执行关键词与正则匹配，毫秒级短路高频已知审计场景（如‘男性做妇科手术’直接命中 GENDER_CONFLICT 算子）；
  2. 第二层（语义与分类）：对于开放式自然语言，由高性价比小模型（如 8B / Flash）结合我们在 ArchetypeRegistry 中沉淀的 7 大审计原型（互斥排他型、伴随依赖缺失型、时序重叠型、药贩子跨机构聚合型等）进行结构化意图抽取与分类；
  3. 复合意图与模糊意图处理：若用户提问模糊或包含复合诉求（如‘查一下去年张三的报销有没有违规，顺便分析全院高频异常药品’），Aligner 会将其判定为复合任务，由 Planner 拆解为多个并行独立的子任务（Sub-tasks），每个子任务打上独立的 Task ID；若模糊到缺失关键主体，系统直接返回澄清提问（Clarification Prompts），拒绝强行猜意图进入执行。”
【深度原理解释】

千万不要一上来就无脑调大模型的 Function Calling，不仅耗时（通常 1~2s），而且当工具多达几十个时，模型的调用准确率会急剧下降。分层漏斗将 80% 的高频确定性问题截流在正则/字典层，只有 20% 的长尾复杂意图交给小模型提取，既节省了 Token 成本，又压低了首字延迟。

Q3 上下文协议 AuditState
上下文通信协议（Context Schema）：你提到的 Context Schema 具体包含哪些字段？在多 Agent 流转时，你是把全量历史对话传给下一个 Agent，还是只传提取后的结构化状态？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们绝对不会在节点间传递全量历史对话，而是基于 LangGraph 定义了严格分层的 AuditState 契约，分三层：

  1. Layer 1（框架通用状态 WorkflowState）：包括 session_id, retry_count, error_log, is_awaiting_human，以及带有滑动窗口消息压缩机制的 messages；
  2. Layer 2（任务中间态 TaskArtifacts）：包括解耦后的结构化意图 tasks、待执行与已执行的 sql_query, sql_history、数据库返回的 raw_data、execution_trace；
  3. Layer 3（领域专属上下文 AuditDomainContext）：包括锁定的审计主体与违规客体 audit_findings、结构化报告 structured_report、反思评价 audit_feedback。

下游 Agent 只订阅它所需的切片字段（State Projection），例如 CoderAgent 只看 tasks、schema_hint 和上一轮报错 error_log，彻底阻断历史废话干扰。”

【深度原理解释】

如果直接把全量 Chat Messages 传给后续 Agent，会产生严重的信息污染（比如上一个 Agent 调用的废弃中间结果、冗余思考过程）。按需结构化抽取不仅将 Token 消耗降低了 60% 以上，更使得每个 Agent 的输入输出具备确定性契约，便于单元测试与重放调试。

Q4 信息衰减 Anchor Pinning
信息衰减问题：当任务链路很长（比如经过“规划 -> 检索 -> 审核 -> 核验”四个节点）时，后面的 Agent 很容易遗忘最初的业务约束或用户核心诉求，你在工程上是怎么解决这种信息衰减的？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们在工程上主要通过两套机制防止信息衰减：

  1. 状态快照只读锚定（Anchor Pinning）：在 Aligner/Planner 节点解析完成后，系统将初始锁定的核心约束（如用户的原始问题 user_question、审计主体 AuditSubject、原型约束 AuditArchetype）持久化写入 AuditDomainContext 的顶层不可变字段，禁止后续节点修改；
  2. Prompt 动态组装前置注入（Prompt Context Assembly）：后续每一个 Agent（无论是 Coder、Critic 还是 Reporter）在组装 Prompt 时，其底层组装器（如 CoderPromptAssembler）强制把不可变的‘审计目标锚点’作为顶级 System 约束拼在最前，与易变上下文（如当前的 SQL、Traceback）做物理区隔，确保任何后续推理都以初始目标为首要参照系。”
【深度原理解释】

大模型存在“迷失在中间（Lost in the Middle）”的注意力缺陷。长链路流转中，多轮工具执行结果和报错堆栈会迅速稀释模型的上下文注意力。把核心业务目标提取为固定的“全局常量”，每次在 Prompt 的最前端和最末端进行强制强化（Recency Bias 利用），能从根本上保证模型在第 4 个节点依然清楚最初的目标。

Q5 防死锁 MAX_RETRIES=1
防死锁与循环控制：在允许局部动态路由或打回重做的节点（比如“核验不通过打回给检索”），如何防止两个 Agent 之间陷入无限互相甩锅的死循环？除了硬编码最大重试次数（Max Iterations），还有什么优雅的降级策略？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们在死循环治理上采取了‘刚性熔断 + 差异化步进反馈 + 状态退避降级’三层机制：

  1. 刚性熔断：在生产环境中设定 MAX_RETRIES = 1（最多允许 1 次定向纠错），坚决杜绝多轮乒乓推诿；
  2. 带差异化诊断记忆的重试（Diagnostic Feedback）：Critic 节点打回时，绝不仅仅返回‘失败’，而是必须通过 ReflectionDiagnosticPolicy 给出具体的归因（例如区分是‘主客体颠倒’还是‘伴随字段单行伪排除’），Coder 在重试时只针对该诊断点调整，若第二次依然失败直接判定此路不通；
  3. 优雅降级（Graceful Degradation）：触发熔断后，系统不直接抛出 500 异常，而是触发降级：通过底层纯代码度量工具（AuditMetricEvaluator）直接根据已有的物理执行数据输出保底底稿，并将报告的风险等级标定为 PENDING_MANUAL_REVIEW，流转至人工待办池。”
【深度原理解释】

多 Agent 交互最忌讳“盲目重试”。如果第一次 SQL 查不出数据是因为数据库根本没有这种违规，LLM 可能会猜想是不是条件太严了，于是胡乱删条件导致全表查出来；或者两个 Agent 一个说 SQL 错了一个说意图错了，无限打架。因此，重试必须带明确诊断指令，且次数必须极其克制（通常 1 次即可判断是偶发格式错误还是根本性逻辑缺陷）。

Q6 并发与隔离 State Reducer
状态机并发与隔离：如果一个复杂任务被拆解为多个子任务并行执行（比如同时查多个政策和明细数据），你的 State Graph 是如何处理并发状态的合并（State Reducer）以及读写冲突的？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“在 LangGraph 的状态管理中，我们针对不同字段定义了专门的 State Reducer（状态合并器）：

  1. 通用消息合并：对于 messages 字段，挂载自定义的 _default_message_reducer，底层通过 trim_and_sanitize 执行去重、清洗与滑动窗口截断；
  2. 子任务产出隔离与追加：对于多子任务并发产出的发现项（audit_findings）或字典，定义为可追加的 Reducer（如 _merge_list），各个并行分支只写入自己局部的 Finding，在 Join 汇聚节点按照 task_id 自动归并；
  3. 覆盖式写入：对于最终的决定性状态（如 sql_query、structured_report），采用自定义的 _overwrite_list 或覆盖逻辑，优先保留最新非空分支的结果；
  4. 并发读写安全：在分布式或多工作线程场景下，利用 Redis 租户级分布式安全锁（RedisSafeLock）对同一 session_id 的状态写入进行原子性保护，防止脏写覆盖。”
【深度原理解释】

原生 Python 字典在多协程并发写入同一状态时极易发生 Key 覆盖或竞态。LangGraph 的核心优势之一就是允许为 State 的每个属性定义 Annotated[Type, reducer_function]。通过严格区分“需追加归并的字段”（列表类成果）和“原子更新的字段”（状态标记），能优雅解决分支并行汇聚冲突。

Q7 粒度拆分 认知解耦
粒度拆分原则：你是依据什么标准把系统拆分成“规划、检索、审核、核验”这几个独立子 Agent 的？如果把“审核”和“核验”合并成一个 Agent 会有什么问题？拆得太细又会带来什么副作用？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们的拆分遵循软件工程的单一职责原则（SRP）与认知解耦（Cognitive Decoupling）：

  • 拆分标准：主要看各环节所需要的‘上下文依赖’与‘系统侧重’。Planner 负责纯业务逻辑推导（System 2 思考），不污染具体的 SQL 语法细节；SQLEXEC 纯粹负责结合物理 Schema 做代码生成与工具调用（System 1 行动）；Critic 拥有独立的审判视角，充当 Evaluator。
  • 合并的危害：如果把‘生成/审核’与‘核验（Critic）’合并，模型会陷入同频幻觉（Self-affirmation Bias）。自己写的 SQL 自己去核查，模型极易产生‘我觉得自己写得完全没问题’的主观固执，必须通过切换独立 System Prompt 与角色的 Critic 节点实现神经符号交叉校验。
  • 过细拆分的副作用：Agent 拆分过细会导致序列化传输开销暴增、端到端延迟翻倍、状态机复杂度陡增，以及长链路传导中的‘信息稀释与失真’。因此我们只保留核心的认知阶段，不在微小步骤上拆 Agent。”
【深度原理解释】

这在业界被称为“生成器-判别器（Actor-Critic）”或“Evaluator-Optimizer”架构。实践证明，用同一个 Prompt 让模型“生成并自我检查”，检出率极低；而让另一个带“挑刺专家”角色的 Critic Agent 来审视结果，拦截主客体颠倒和语法陷阱的成功率能提升 40% 以上。

【面试标准回答】 点击内容区显示/隐藏答案

“我们底层选用了 LangGraph 作为有向无环图（DAG）及带环状态图的基础框架，但在其之上针对医保审计业务做了深度的自主封装与中间件拦截：

为什么选 LangGraph 而不是 AutoGen？ AutoGen 偏向拟人化对话，在需要确定性流程控制的严肃业务中极难收敛；LangGraph 原生基于图状态机，支持显式条件路由与持久化，工程契约更清晰。

踩过的主要坑与应对：

  1. 状态臃肿与序列化瓶颈：LangGraph 默认的 State 容易在多轮迭代中无限累加导致序列化性能暴跌，我们通过自研的 state_governance 实现了严格的分层状态管理和消息清洗截断；
  2. 异常处理机制不透明：原生图执行报错时往往全局崩溃，我们在节点外层封装了 pipeline_tracker 与独立深模块，实现了节点级沙箱捕获与白盒追踪。”
【深度原理解释】

很多团队盲目从零手写状态机，最后发现重做了线程池调度、异步协程管理、条件分支判定、状态快照回退等基础轮子，维护成本极高。借助 LangGraph 提供的图骨架，将业务重心放在自定义 Gate 拦截器、SQL 安全沙箱与上下文组装等高价值模块，是企业级落地性价比最高的做法。

Q9 持久化 Checkpointer
长周期任务与断点续传：如果工作流执行到第 3 个 Agent 时因为网络波动或服务重启中断了，你的状态机支持状态持久化（Checkpointer）和从断点恢复执行吗？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“是的，系统原生支持断点续传。我们通过为 LangGraph 挂载外部持久化 Checkpointer（开发测试环境为 SQLite，生产环境为 PostgreSQL/Redis）：

  1. 状态自动快照：每个节点执行完毕并通过 Gate 校验后，调度器会自动将当前 AuditState 的增量 Diff 结合 thread_id 和 checkpoint_id 持久化到存储介质；
  2. 故障拉起与幂等恢复：当节点因网络中断或进程崩溃重启后，系统根据会话 thread_id 从数据库检索最新的合法 Checkpoint，重建内存图状态，直接从中断的下游节点继续向下流转，而无需从头重新调用前置的 Planner 或大模型，既保障了长任务可靠性，又避免了重复消耗 Token。”
【深度原理解释】

在大数据量审计或多表复杂查询中，一个审计任务可能耗时十几秒到数分钟。没有 Checkpoint 机制意味着任何网络抖动都会让昂贵的 LLM 推理与数据库查询前功尽弃。通过快照持久化，配合幂等性设计（执行过的 SQL 记录在 sql_history 中），可以做到“无感断点恢复”。

Q10 Human-in-the-loop TaskPool
人工介入（Human-in-the-loop）：在审核或核验这类高风险节点，如果 Agent 置信度不足需要人工确认，你的状态机如何实现挂起（Suspend）、等待外部信号回调后再继续流转？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们在状态机中设计了专门的 HUMAN_APPROVAL 挂起节点与动态任务池（Task Pool）机制：

  1. 挂起判定：当 Critic 或安全哨兵检测到高风险异常（例如涉案金额巨大但置信度低于阈值、或触发了高危规则变更时），SQLEXEC 后的条件边会直接路由至 HUMAN_APPROVAL 节点；
  2. 任务提报与中断：该节点将当前完整快照注册至分布式 task_pool.submit_task(thread_id, state, reason)，将状态标记为 is_awaiting_human=True，随后工作流直接流转至 END 释放工作线程；
  3. 异步回调恢复：当医保专家在后台界面完成核验并提交修正意见后，API 服务接收到 Webhook 回调，携带专家的批注输入通过图执行器的 resume 接口唤醒原会话，直接跳转至下一步（如 Reporter 渲染）继续流转。”
【深度原理解释】

千万不要在进程内 time.sleep() 阻塞等待人工！在分布式生产架构中，人工可能几个小时甚至几天后才审批。必须将状态机持久化入库，进程优雅退出；待审批通过后，通过 API 唤醒携带人工修正参数从当前检查点继续走，这才是真正的工业级 Human-in-the-loop。

Q11 Chunking 文档切片
切片策略（Chunking）：在处理复杂的业务规则或政策文档时，你是怎么切分文档的？如果遇到跨段落的条款、带有多层标题的文档或者文档内嵌表格，普通按字符长度切分导致语义截断怎么解决？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们彻底摒弃了朴素的‘固定字符长度切分（Fixed-size Chunking）’，采用了层次化结构感知切片（Hierarchical & Markdown-Aware Chunking）：

  1. 层级标题感知：基于 AST 解析医保政策的树状目录结构（章、节、条、款），将上级各级标题作为元数据与‘面包屑上下文（Breadcrumbs Context）’，强制前置拼接到该条款的具体正文切片中，避免孤立条款丢失适用范围；
  2. 内嵌表格原子化：对于诊疗项目收费标准、医保报销比例等内嵌表格，将其整体序列化为标准 Markdown 表格或结构化 Key-Value，视为不可分割的‘原子 Chunk’，严禁从表格中间按字符斩断；
  3. 滑动重叠与语义边界对齐：对于超长条款，优先在句号、分号处截断，并保留 15%~20% 的语义滑动窗口（Overlap），从根本上消除跨段落条件与前提约束被截断的假阳性问题。”
【深度原理解释】

例如某政策规定：“第一章 住院医疗费用管理... 第三条 下列情况不予报销：(1) 美容整形；(2) 减肥项目”。如果单纯按长度切分，切出来的片段只有“(1) 美容整形；(2) 减肥项目”，检索出来后模型根本不知道这是“属于住院还是门诊”、是“报销”还是“不予报销”。把父级路径作为元数据注入切片，是专业领域 RAG 的核心基本功。

Q12 混合检索 RRF 融合
混合检索权重融合：向量检索（Dense）和 BM25（Sparse）各自的优劣势是什么？在你的系统里，两路召回的结果是如何进行分数归一化或融合的（比如 RRF 倒数秩融合算法，还是加权打分）？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“在医保场景下，两者的互补性极强：

  • Dense（向量检索）：优势在于语义泛化与意图模糊匹配（比如用户输入‘超标买补药’能召回‘滋补中药超限使用’），但劣势是对生僻专有名词、药品代码、耗材编码（如 YB0102001）极度不敏感，易产生虚假相似度；
  • Sparse（BM25 稀疏检索）：优势是对精准专有名词、医保编码、特定条款序号拥有 100% 命中能力，但无法处理同义词替换。

融合方案：我们采用 RRF（Reciprocal Rank Fusion，倒数秩融合） 而非线性加权打分。因为 Dense 的余弦相似度与 BM25 的 TF-IDF 得分处于完全不同的尺度空间，Min-Max 归一化极易受到极值干扰；而 RRF 只看两路召回的绝对排名（公式：RRF_Score = Σ 1 / (k + rank_i)，常数 k=60），无论底层分值怎么波动，排名越靠前的交集文档最终得分越高，工程稳定性极佳。”

【深度原理解释】

线性打分（如 0.7 * Dense + 0.3 * BM25）在实际调参时非常痛苦，因为换一个 Embedding 模型或者换一批长短不同的文档，Dense 和 BM25 的分值分布就会剧烈漂移，每次都要重新校准超参数。RRF 完全摆脱了分值维度的束缚，只依赖相对排序，是目前工业级混合检索公认鲁棒性最高的方法。

Q13 Rerank BGE-Reranker-large
Rerank 的收益与代价：引入 Rerank 模型后，召回准确率提升了多少？Rerank 会增加明显的推理延迟，你的 Top-K 漏斗是怎么设置的（比如粗排召回多少条，精排保留多少条喂给 LLM）？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“在引入 Cross-Encoder 架构的 BGE-Reranker-large 模型后，我们业务场景下的 Top-3 召回准确率（Hit@3）从原本混合检索的 78.5% 跃升到了 92.3%，彻底解决了 Bi-Encoder 向量空间无法捕捉深层交叉语义的问题。

针对 Rerank 带来的计算延迟，我们构建了两阶段漏斗（Two-stage Funnel）：

  1. 粗排阶段（召回）：Qdrant 向量检索召回 Top-30，BM25 召回 Top-30，经 RRF 融合去重后截取 Top-20；
  2. 精排阶段（Rerank）：仅将这 Top-20 条候选送入本地部署并经过 TensorRT 优化的 BGE-Reranker，将端到端延迟严格压制在 35ms 以内；
  3. 上下文注入：最终仅筛选前 Top-3 ~ Top-5 条核心政策依据注入 LLM 上下文，既保证了关键证据无遗漏，又防止长 Prompt 增加 LLM 生成延迟。”
【深度原理解释】

为什么 Bi-Encoder（向量检索）不够？因为向量检索是把 Query 和 Document 分别独立编码成向量再求内积，两个文本之间没有任何 Token 级别的交叉注意力（Cross-attention）。而 Reranker 把 Query 和 Document 拼在一起送入 Transformer，每个字互相做 Attention，虽然慢，但判断相关性极其精准。用 Top-20 漏斗控制 Rerank 计算量，是兼顾准确率与性能的工业级标准姿态。

Q14 Few-shot 防投毒门禁
动态 Few-shot 注入：在 Text-to-SQL 中，动态 Few-shot 是怎么检索的？是匹配用户问题的字面相似度，还是匹配问题背后的 SQL 语法结构相似度？样本库是怎么构建和维护的？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“如果仅靠字面相似度检索 Few-shot，经常会召回‘业务看起来像、但 SQL 语法结构风马牛不相及’的错误样本。我们的解决方案是‘意图原型驱动的混合语义检索 + 防投毒门禁’：

  1. 样本向量化特征：在向量库（Qdrant）构建 Golden Examples 时，索引的内容不仅是问题文本，更是通过‘自然语言问题 + 审计原型标签（如伴随依赖、时序重叠、自连接套收）+ 目标表名’拼接后的结构化特征；
  2. 检索对齐：检索时优先按照 Aligner 判定的 AuditArchetype 进行软过滤，确保召回的示范样本在 SQL 拓扑结构上（比如都是跨行子查询对撞）高度一致；
  3. 防投毒门禁（Anti-Poisoning Gate）：只有人工复核过、或者在生产环境中经过 SQLGuardian 严格 AST 语法审计无恒假矛盾、且执行结果验证通过的优质 SQL 才能通过 Consolidator 入库，杜绝脏数据污染检索库。”
【深度原理解释】

例如用户问：“查张三有没有同时在两家医院住院”，如果按字面查，可能召回“查张三的住院总费用”；但按“时序重叠型（Temporal Overlap）”原型检索，召回的样本就会教模型如何写 A.in_time < B.out_time AND A.out_time > B.in_time 的区间重叠 SQL。教模型“语法结构与逻辑拓扑”远比教它“匹配关键词”更重要。

Q15 Schema Linking SceneTableSelector
数据库 Schema 裁剪：如果生产环境有几百张表、上千个字段，不可能全部塞进 Prompt。你的 Schema 裁剪（Schema Linking）具体是怎么做的？如果裁剪阶段漏掉了关键关联表，后续怎么补救？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们设计了 SceneTableSelector + TableRelationLinker + AdaptiveSelector 的多级裁剪体系：

  1. 表级裁剪（Table Linking）：建立领域映射注册表 configs/schema_registry.yaml。当问题分类器识别出场景（如‘结算明细违规’），直接命中核心大宽表 fqz_fymx_test；若涉及字典或目录核查，自动关联 fqz_fyml_test，从数百张表中锁定 1~3 张核心表；
  2. 列级裁剪（Column Pruning）：通过词表匹配与字段图谱（FieldKnowledgeGraph），只提取与问题相关的列及其注释，将上百个冗余字段剔除；
  3. 漏表动态补救机制：如果在 SQLEXEC 阶段出现 Unknown identifier 或在 AST 静态预检中发现缺少 JOIN 必要外键，Coder 捕获该异常并向 TableRelationLinker 抛出拓扑补齐请求，根据元数据图谱动态将缺失的关联表补入下一次重试的上下文。”
【深度原理解释】

塞全量 Schema 是很多初级 RAG/Text-to-SQL 系统崩溃的元凶：不仅会导致 Prompt 长度瞬间超出 10K 甚至 30K Tokens，更容易让模型在几十个同名字段（如各表的 create_time, id, org_code）中挑错列。基于领域元数据进行自适应收敛，既保证了准确率，又大幅压低了推理成本。

Q16 语义对齐 SSOT 枚举契约
隐式业务逻辑与黑话对齐：用户提问往往用业务黑话（比如“违规套现”、“超标刷卡”），而数据库字段是枯燥的英文缩写或状态码（如 status = 3），你如何解决非结构化问题与结构化枚举值之间的语义鸿沟？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“在医保行业中，黑话和字段之间存在巨大的鸿沟。我们通过‘单一事实源枚举契约（Single Source of Truth Enum Contract）+ 字段知识图谱（FieldKnowledgeGraph）’来拉齐：

  1. 物理注册与正向对齐：所有物理字段的取值规范唯一注册在 schema_registry.yaml 中。例如，业务上‘男性使用妇科栓剂’，在知识库中明确注册：gend 字段中 '1' 代表男性（且物理库可能带尾部制表符，统一对齐为 gend LIKE '1%'），'2' 代表女性；
  2. 黑话概念映射：在 Prompt 注入前，通过 FieldKnowledgeGraph 执行预处理，将用户提问中的业务概念（如‘退费冲正’）直接翻译为底层语义约束（det_item_fee_sumamt < 0，且数量 cnt 为负数，不是聚合计数）；
  3. 严禁模型自由臆测：提示词中明确禁止模型脑补状态码，所有枚举值全部通过 AdaptiveSelector 由注册表动态注入到 System Context 中作为强行约束。”
【深度原理解释】

很多大模型直接写出来的 SQL 会想当然地写出 WHERE status = '违规' 或者 WHERE gender = '男'，而在实际医保物理表中存储的往往是国标码或特定历史系统的数值（如 1、2、01）。靠 Prompt 叮嘱模型“不要猜”是防不住的，必须在工程层维护权威的术语词典，并在 Prompt 中以“物理定义与示范”的形式喂给模型。

Q17 SQLGuardian sqlglot AST
SQL 语法预检与安全拦截：你提到的“SQL 语法预检机制”具体检查什么？是用 AST（抽象语法树，如 sqlglot）做静态解析，还是用数据库的 EXPLAIN？如何从根源上防止大模型生成 DROP、DELETE 或导致全表扫描的慢查询（Slow Query）？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们的 SQLGuardian 采用的是双重防护：前置 AST 静态安全与逻辑审计（sqlglot）+ 底层只读物理限制：

  1. AST 静态安全拦截：使用 sqlglot 将模型生成的 SQL 解析为抽象语法树，遍历所有 AST 节点，严禁出现 DROP, DELETE, UPDATE, ALTER, TRUNCATE 等任何非只读节点，违者直接阻断并报错；
  2. 恒假互斥与逻辑陷阱防御（Contradiction Predicate）：通过静态 AST 检查是否存在布尔矛盾，如二元枚举全排除（gend NOT LIKE '1%' AND gend NOT LIKE '2%'）、上下界区间倒置（amt > 1000 AND amt < 100）、伴随缺失单行伪排除等，在物理执行前 100% 静态拦截；
  3. 慢查询与全表扫描防御：在 AST 层强制检查是否命中分区字段（如医保结算日期 setl_time）；如未声明分区，AST 重写器会自动注入默认时间窗口与强制 LIMIT 1000 采样；同时在 ClickHouse 数据库账号权限上严格配置为 readonly=1，并在引擎层设置 max_execution_time=10 秒与 max_rows_to_read 硬件级熔断。”
【深度原理解释】

绝对不能依赖数据库驱动的简单字符串判断，因为模型可能会用注释绕过（如 SELECT ...; -- DROP TABLE）。基于 AST 的解析能穿透一切文本变形，精准识别真正的语法操作类型。同时，医保流水表通常有数十亿行，如果不强制在 AST 检查分区和 LIMIT，一条全表聚合 SQL 就能直接打崩生产分析引擎。

Q18 空集诊断 Zero-Findings Baseline
Text-to-SQL 自适应修正边界：当把数据库 Traceback 回传给大模型修正时，最常见的是哪类错误（如列名幻觉、GROUP BY 语法错误、JOIN 条件缺失）？如果生成的 SQL 语法完全正确、执行不报错，但查出来的业务逻辑是错的（或返回空集），你的系统怎么发现并拦截？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“在实际生产中，最隐蔽、杀伤力最大的不是语法报错，而是‘语法完全合法，但因逻辑颠倒暗中返回 0 行’。

针对空集问题，我们设计了‘零发现基线判定与主客体一致性核验’（QualityGate 规则集）：

  1. 真合规 vs 伪合规甄别：当 ClickHouse 返回 0 行时，系统绝不直接采信。此时 Critic 节点会介入，对比 tasks 中的主体定义与 SQL WHERE 子句：检查是否发生了‘将客体特征当成主体过滤’（例如‘查男性使用节育器’，错误写成了 WHERE gend = '2' 导致 0 结果）；
  2. 恒假逻辑检测：通过 ContradictionDetector 回溯 SQL 是否存在恒假逻辑（如互斥条件并列）；
  3. 自愈反思触发：如果判定为伪合规，Critic 会生成明确的诊断记忆（‘检测到主体条件颠倒，应使用 gend=1’），回传给 Coder 执行仅限 1 次的定向纠错；只有当逻辑核查完全无误且确认全库确实无此违规时，才作为‘零发现基线合规（Zero-Findings Baseline）’正常放行。”
【深度原理解释】

在传统 Text-to-SQL 中，查出 0 条数据，开发者很容易误以为“系统很健康、没有违规数据”。但在医保审计中，90% 的 0 数据都是因为大模型把主体条件写反了，或者在单条明细记录上写了互斥条件。如果不设立针对“0 命中”的逻辑审计门控，系统就会漏掉几乎所有的真实违规案件。

Q19 跨源联动 串行解耦拓扑
跨源数据联动：当一个审核任务既需要去向量库查非结构化政策（RAG），又需要去关系型数据库查结构化流水（Text-to-SQL）时，这两步是串行还是并行？如何用查出来的政策阈值去动态指导 SQL 的生成？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们在架构上严格采用‘串行解耦拓扑（Serial Decoupled Pipeline）’：

  1. 前置 RAG 政策提取：在进入 SQL 编写之前，Planner 必须先调用向量检索与 Rerank 查出相关政策文档（例如《某市门诊慢特病结算规定》）；
  2. 结构化参数提炼（Parameter Grounding）：由 Planner 从非结构化文本中抽取出明确的定性与定量门槛（如：高血压开药量不超过 30 天，单笔报销上限 500 元），转化为强类型的结构化参数注入 methodology 字段；
  3. 参数作为常量传递给 Coder：CoderAgent 在组装 SQL 时，直接引用 Planner 提炼出的硬指标作为 SQL WHERE 或 HAVING 的数值阈值（例如 HAVING sum(cnt) > 30），坚决杜绝让 Coder 边看原始政策长篇大论、边猜着写 SQL。”
【深度原理解释】

如果并行执行，不仅逻辑上说不通（SQL 根本不知道过滤阈值是多少），而且会导致两个子任务争抢上下文注意力。让专业的人做专业的事：检索负责拿政策，Planner 负责把自然语言政策定型为“数值与规则算子”，Coder 负责拿确定的数值翻译为 ClickHouse 语法，责任边界极其清晰。

Q20 工具幻觉 Tool Scoping
工具调用幻觉：当挂载的工具较多时，模型可能会选错工具，或者编造工具所需的必填参数。你在 Tool Description 和参数约束上做了哪些工程优化？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们主要通过三层工程手段遏制工具调用幻觉：

  1. 工具集上下文隔离与动态挂载（Tool Scoping）：不在一个全局会话中挂载所有工具。在 Planner 节点，只暴露只读检索与元数据工具；在 SQLEXEC 节点，只暴露只读数据库执行与校验工具，物理消除‘跨阶段选错工具’的可能；
  2. 契约化 Description 设计：在 Tool Description 中明确编写‘Negative Constraints（反向禁令）’和‘适用场景正向用例’，明确指出‘当需要查某明细时严禁调用本工具，应调用 XXX’；
  3. Pydantic 严格模式绑定（Strict Schema Binding）：每个工具的入参均采用 Pydantic v2 定义，所有字段明确标明类型、正则校验器与默认值，并开启模型的 strict=True 结构化参数输出模式，让底层直接通过受限解码 FSM 拦截参数格式幻觉。”
【深度原理解释】

很多 Agent 系统把十几二十个工具平铺给 LLM，这在模型看来就像面对一个巨大的迷宫。根据状态机的当前节点动态裁剪暴露的工具列表，能直接把工具选择的复杂度从 O(N) 降到 O(1)，从根源上消除了工具调用的混乱。

Q22 结构化对比 FSM vs 业务门禁
结构化输出方式对比：现在很多大模型原生支持 response_format={"type": "json_object"} 或 Structured Outputs（基于受限解码 FSM），为什么还需要自己写 Pydantic 拦截器与自愈重试管道？这两者有什么本质区别？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“原生的 Structured Outputs 解决的是‘语法合规（Syntax Compliance）’，而我们的 Pydantic 拦截器与自愈管道解决的是‘语义真理与业务合规（Semantic Truth & Business Compliance）’：

  1. 局限性：厂商原生的受限解码（FSM）只能保证输出的 JSON 严格符合 Schema 定义的字段类型（例如 amount 确实是个 float），但它完全无法保证这个 amount 是否符合业务逻辑（比如模型完全可以合规地输出一个 amount: -99999，或者伪造一条合规数据）；
  2. 多模型生态兼容：很多优秀的开源模型或轻量推理引擎对原生 JSON Schema 支持并不完善，强依赖厂商特有 API 会丧失底层模型切换的自由度；
  3. 自愈管道的价值：当深层业务校验未通过时，原生的 API 是无法感知的；必须靠我们的外层拦截器捕获 ValidationError，并携带具体的业务诊断信息驱动模型执行精准自愈。”
【深度原理解释】

把“格式正确”等同于“结果正确”是做 Agent 最常见的误区。FSM 能保证括号闭合、字段齐全，但决定数据能不能用于实际审计执法的，是后面的客观业务逻辑。因此，Pydantic 业务门禁不仅不能砍，反而是保证系统严肃可信的核心生命线。

自愈重试 Prompt 组装：当捕获到 ValidationError 时，你是如何构造修正 Prompt 的？是把原始长 Prompt、错误输出和报错信息全部拼在一起重发，还是只截取局部上下文？如何避免重试导致 Token 消耗翻倍？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“我们绝对不会把全量长 Prompt 和历史重新打包发送，而是采用‘局部增量诊断重试（Delta Context Repair）’：

  1. 报错精准裁剪：捕获 Pydantic 的 ValidationError.errors()，只提取具体的错误定位路径（loc）和错误原因（msg），例如只提取 findings[0].amount: 金额不能为负数；
  2. 局部上下文切片：仅携带：① 核心指令摘要；② 模型上一轮输出的有缺陷的 JSON 片段；③ 裁剪后的报错诊断明细；④ 一句强制修复约束（‘请仅针对上述指出的字段错误进行修正，直接输出修复后的完整 JSON’）；
  3. 收益：这种组装方式将原本可能需要消耗 8K~15K Tokens 的长上下文直接压缩至 800 Tokens 以内，Token 开销削减了 80% 以上，同时因没有长距离噪音干扰，模型的单次修复成功率高达 95% 以上。”
【深度原理解释】

把原 Prompt + 错误堆栈全部原样发回去，模型往往会“不知道自己到底错在哪里”，反而因为上下文太长注意力涣散，在修改 A 错误的同时又把原来正确的 B 字段给改错了。给出像编译器一样的精准局部定位（类似“第几行第几个字段是什么错误”），模型能以最小的算力消耗快速精准改正。

Q30 防合规幻觉 Explicit Nullability
防止纠偏引发新幻觉：在触发自愈重试时，有时候模型为了强行迎合 Pydantic 的字段类型要求（比如某个必填字段找不到对应信息），会选择“胡编乱造”一个合法的值来通过校验。你如何在 Schema 设计上防止这种“为了合规而产生幻觉”的现象？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“在工业界，这种现象叫‘合规逼迫型幻觉（Compliance-driven Hallucination）’。我们在 Schema 设计和提示词工程中采用了三项防腐设计：

  1. 允许可空与未知类型（Explicit Nullability）：在 Schema 定义上，杜绝盲目设置必填；对于非关键或从上下文中可能无法推断的字段，严格声明为 Optional[T] = None；
  2. 设计‘无法判定’的合法枚举（Explicit Unknown Enum）：例如在违规原因或依据字段中，显式提供 'UNCONFIRMED'、'NOT_SPECIFIED' 或 'DATA_ABSENT' 枚举选项，并在 System Prompt 中反复强调：‘若证据不足以支撑结论，必须明确填入 UNCONFIRMED，严禁自行揣测’；
  3. 置信度门禁（Confidence Score Gate）：在 Finding 模型中增加 confidence_score: float 字段。如果模型必须填写某字段，要求其同步输出置信度；后置拦截器若发现其给出的字段虽然格式合法，但置信度得分过低，自动剥离该字段并将其转入人工待办复核，杜绝以假乱真。”
【深度原理解释】

如果你的 Pydantic 模型里每个字段都是必填（比如必须填写违规政策编号、必须填写责任医生工号），而这篇就诊明细里根本就没提供医生工号，大模型在被报错打回后，为了通过程序校验，唯一的选择就是硬编一个“DOC9999”。给大模型留出合法的“我不知道”的退路，配合置信度后验，是解决高风险场景下模型胡编乱造的关键解法。

  2. 状态快照与时间旅行：Checkpointer 每个节点自动存快照，支持断点续跑（不重复调用昂贵 LLM）和回滚到某一轮重新分叉；手写要自己重造轮子。
  3. 非阻塞的 Human-in-the-loop：进入 HUMAN_APPROVAL 时持久化状态并释放线程，审批后用 API 唤醒继续，而不是 sleep 或轮询。
  4. 声明式 State Reducer：并行分支的状态合并通过 Annotated[Type, reducer] 声明，免去到处加锁和手写合并。

结论：无环固定数据管道用 ETL 工作流；需要带环自愈、人工挂起、状态回溯的 LLM 业务，LangGraph 更合适。”

【深度原理解释 / 追问拆招】

追问 A：Temporal / Camunda 也支持长等待和断点恢复，为什么不用？

  • 运维重：它们需要独立集群与 Worker 守护；LangGraph 是内嵌在 FastAPI 进程里的轻量库。
  • 缺少 LLM 语义：LangGraph 与 LangChain/LangSmith 同生态，对流式输出、BaseMessage、工具协议、Prompt 追踪原生契合；Temporal 里要自己写序列化胶水。
  • 承认：做大型跨服务分布式事务编排时，Temporal 仍是更好的选择。

  • 标志位膨胀（is_retry / need_critic / turn_count），分支逻辑成面条代码；

“伴随缺失”与“单行伪排除反模式”到底是什么？举个例子看懂。
▼
【面试标准回答】 点击内容区显示/隐藏答案

“费用明细表每行只代表一个收费项目。‘无手术收麻醉费’不能在单行里写 LIKE '%麻醉%' AND NOT LIKE '%手术%'——因为任何麻醉行本身的名称都不含‘手术’，会让所有正常的麻醉费 100% 被判违规。正确做法是在就诊/结算粒度（setl_id）跨行核对：麻醉行所在的结算单里，是否存在手术行。我们把它归为 MISSING_COMPANION 原型，由 QualityGate 规则强制要求子查询 NOT IN 或 LEFT JOIN … IS NULL。”

【直观例子：张三 vs 李四】

21001张三阑尾切除手术3000做了手术

❌ 错误 SQL（单行伪排除）

SELECT * FROM 费用明细表
WHERE 收费项目 LIKE '%麻醉%'
  AND 收费项目 NOT LIKE '%手术%';
-- 第 3 行“全身麻醉费”本身不含“手术”二字 → 张三也被抓 → 全省合法麻醉全部误报

✅ 正确 SQL（跨行子查询）

SELECT * FROM 费用明细表
WHERE 收费项目 LIKE '%麻醉%'
  AND 结算单号 NOT IN (
      SELECT 结算单号 FROM 费用明细表 WHERE 收费项目 LIKE '%手术%'
  );
-- 子查询返回 [1001] → 排除张三；1002 不在其中 → 只抓出李四

源码 4 分位数 Quantile / P95
什么是分位数计算？为什么在 Top-10 任务里先算分位数是灾难？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“分位数是‘排位门槛线’：P95 = 5000 元表示 95% 的数据都在 5000 元以下，只有前 5% 超过。审计里常用 P95/P99 当异常基线，因为平均数会被极端值拉偏。但对于‘取最高的前 10 名’，先算全表 P95 再过滤再排序是多此一举：前 10 名一定远高于 P95，而精确分位数要把数亿行载入内存做排序/聚合，耗时长、内存大；直接 ORDER BY … DESC LIMIT 10 只需维护一个大小为 10 的堆。”

【深度原理解释】

通俗类比

  • P50（中位数）：1000 万考生排队，站在正中间的成绩；
  • P90：前 10% 的门槛；P95：前 5% 的门槛；P99：前 1% 的门槛。

ClickHouse 写法

SELECT quantile(0.95)(det_item_fee_sumamt) AS p95_fee FROM fqz_fymx_test;
做法底层执行代价
直接取前 10
ORDER BY fee DESC LIMIT 10		只需维护大小为 10 的小顶堆，流式扫描一遍内存极小，速度快
先算分位数再过滤
quantile(0.95)(fee)		需对全量数据做分位聚合（精确版本要保留大量数据）耗时更长、内存占用更高，数据量大时可能超时/OOM
表述提醒：ClickHouse 默认的 quantile 是近似算法（采样），quantileExact 才是精确算法且最耗内存。面试时可说“精确分位数”开销大；别笼统说“一定会 OOM”，说“可能超时或内存压力大”更严谨。
源码 5 MySQL 优先队列 / 堆
MySQL 的 ORDER BY … LIMIT N 是用小顶堆实现的吗？
▼
【面试标准回答】 点击内容区显示/隐藏答案

“是的。排序列没有可用索引时，MySQL 的 filesort 在 LIMIT 较小、堆能放进 sort_buffer 的情况下，会使用优先队列（堆）优化：只维护容量为 N 的堆，流式扫描全表，新记录只和堆顶比较，更优则替换堆顶；扫完后堆里就是 Top-N。时间复杂度约 O(M log N)，内存只需 N 条记录。而如果排序列有索引，直接沿 B+ 树有序叶子取前 N 条即可，连堆都不需要。”

【深度原理解释】
档位条件做法
第一档（最快）排序列有索引且可用顺着 B+ 树有序叶子直接取前 N 条，无需排序
第二档无索引，LIMIT 小，堆能放进 sort_bufferfilesort + 优先队列（堆）优化
第三档无索引，LIMIT/OFFSET 很大（如深度分页）堆放不下，退化为全量排序，必要时落临时文件做多路归并
